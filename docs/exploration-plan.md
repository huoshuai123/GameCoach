# 4 周探索计划：雀魂 AI 复盘教练优先

## Summary

长期母题：做 **多游戏教练 AI**，核心资产是可迁移的 **局势评估引擎**。

第一阶段不急着创业化或全面产品化，而是用 4 周优先探索 **雀魂 AI 复盘教练**。本阶段实现形态以 **Android 工程** 为主，目标是做出能在移动端完整体验的本地复盘 Demo；同时通过规范文档、报告 schema 和平台无关的领域模型，给未来迁移到 Web、桌面、iOS 或服务端留足空间。

三国志 11 真人感 AI Mod 不再作为第一阶段并行 Demo，只作为未来多游戏教练 AI 的扩展候选和设计参考。

## 核心资产

共用能力：

- 解析复杂局势状态。
- 评估优势、风险、机会、关键决策点。
- 输出人能理解、能指导训练的解释。
- 在不同游戏之间复用报告结构和局势评估边界。

第一版继续沉淀一个轻量局势评估模型：

- `Situation`：任意游戏局势。
- `Metric`：可比较的局势指标。
- `DecisionPoint`：关键决策点。
- `EvaluationReport`：可展示给玩家的评估报告。
- `GameAdapter`：游戏接入层，雀魂是第一个实现对象。

## 第 1 周：雀魂基础调研与 Android 骨架

目标：

- 验证雀魂牌谱解析可行性和合规边界。
- 定义雀魂牌谱数据格式草案。
- 确定 Android 工程分层：UI、Domain、Data、Evaluator。
- 明确哪些能力必须保持平台无关，避免被 Android 细节绑死。

产出：

- 雀魂牌谱数据格式草案。
- Android 工程骨架设计说明。
- 合规边界说明：不做实时辅助、不做账号登录、不做平台规则风险高的自动化。
- 跨端迁移契约初稿。

## 第 2 周：Android 本地 Demo

目标：

- 做出 Android 本地可演示 Demo。
- 完成样例牌谱导入、关键决策点识别、复盘报告展示。
- 重点不是完美判断，而是报告是否有“教练感”。

第一版分析重点：

- 打牌效率。
- 危险度。
- 攻守判断。

验收：

- 样例牌谱能在 Android Demo 中导入。
- 每局报告指出 3-5 个关键决策点。
- 每个点包含巡目、玩家选择、推荐选择、问题类型、解释和训练建议。
- Python 原型仍可作为算法和报告结构验证层运行。

## 第 3 周：教练感打磨

目标：

- 优化解释质量、训练建议和报告结构。
- 增加样例覆盖，确认 Demo 能稳定指出值得复盘的点。
- 让 Android 端体验像一个复盘教练，而不是纯规则输出器。

重点：

- 报告先给结论，再解释原因。
- 训练建议要具体到下一次对局能尝试的动作。
- 决策点优先级要清晰，避免把所有小失误堆在一起。

验收：

- 至少测试 10 局结构化牌谱样例。
- 每局报告能稳定产出 3-5 个高价值决策点。
- 报告内容符合 `review-report-schema.md`。

## 第 4 周：评估与迁移规范

目标：

- 评估是否继续投入雀魂 AI 复盘教练。
- 整理 Android 到其他端的迁移规范。
- 明确多游戏教练 AI 的下一阶段扩展方式。

评分维度：

- 兴奋度。
- 雀魂复盘质量。
- Android 产品手感。
- 技术可行性。
- 跨端迁移准备度。
- 多游戏扩展空间。

验收：

- README、探索计划和候选归档口径一致。
- Android 架构文档、报告 schema、跨端契约完整可读。
- 明确下一阶段是继续打磨雀魂，还是开始抽象第二个游戏 adapter。

## Assumptions

- 第一阶段成功标准不是赚钱，也不是用户规模，而是 **是否兴奋到愿意继续做**。
- 本次计划调整只修改文档和方向，不立即创建 Android 工程。
- 当前 Python 代码继续作为算法和报告结构原型保留。
- 候选 B“截图式数码家电购买参谋”暂时保存为大众产品备选，但不作为当前主线。
- 三国志 11 方向保留为未来多游戏教练 AI 的扩展候选，不作为本阶段必须交付 Demo。
